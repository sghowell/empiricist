  > **UPDATE 3 (COMPILE-TIME POISON-IMPORT fix — the 4th break; supersedes the sandbox/import posture of UPDATE 2, which it otherwise retains).** UPDATE 2's kernel anchor was defeated a 4th time by attacking the *environment the compile runs in*, not the kernel. **Root cause: the verifier let untrusted Lean EXECUTE ARBITRARY IO AT ELABORATION in a shared, writable, non-sandboxed environment** (gate-b compiled at `SandboxMode.NONE`, real HOME, with the *writable* project build lib on the compile/checker `LEAN_PATH`) — violating the project non-negotiable "the model never gets a shell". The exploit: call-1's compile-time `#eval` (runs at elaboration) writes a POISON olean — `theorem EmpiricistLean.Poison.boom : False` built via `(getEnv).addDeclCore … (doCheck := false)` with value `Eq.refl` (compiles clean, `collectAxioms=[]`) — into `.lake/build/lib/lean/EmpiricistLean/Poison.olean`. Per-call cleanup only removed `<tok>` files, so the poison PERSISTED. Call-2 does `import EmpiricistLean.Poison; theorem grandclaim : (2:Nat)=3 := Poison.boom.elim`; `leanchecker` TRUSTS the import (it only replays the *module's own* added decls, not its imports' internals), exits 0, and `verify()` returns **PASS on `2=3`** with an attacker-chosen `statement` (`… : RiemannHypothesis := boom.elim` → PASS statement="RiemannHypothesis"). **The fix closes the CLASS with three independent levers (`verifiers/lean.py`, `version` `3.0`→`3.1`).**
  > - **LEVER 1 — sandbox the untrusted compile.** Every subprocess that touches untrusted source — compile (b), import probe (b2), kernel re-check (c), axiom/statement audit (d) — runs through `executor.execute()` with `SandboxMode.SANDBOX_EXEC` and an **ephemeral per-call workdir**: network denied, filesystem **writes confined to that workdir**. A compile-time `#eval IO.FS.writeFile "<shared build lib>/…/Poison.olean"` (or the same via a spawned `sh -c` — descendants inherit the sandbox) is DENIED ("operation not permitted"); the toolchain (`~/.elan/…`) and pinned mathlib/Basic oleans are READ-only inputs (allowed by the profile's default-read posture). Because `lake`'s own build-dir writes fight the sandbox, we resolve the pinned toolchain binaries + `LEAN_PATH` ONCE via `lake env` (trusted, unsandboxed, at setup) and invoke `lean`/`leanchecker`/`axiom_audit` **directly** with an explicit `-o <ephemeral>/…` and a restricted `LEAN_PATH` — so a direct binary writes only its `-o` target (in the workdir). *Proven:* a compile-time `#eval`/`sh` write outside the workdir is denied and the shared-lib poison never materializes.
  > - **LEVER 2 — pin the import closure.** The compile/checker `LEAN_PATH` is built from ONLY pinned-trusted roots: the pinned mathlib + package build libs, the toolchain lib, a **read-only copy** of our `EmpiricistLean.Basic` olean (staged outside any sandbox workdir, atomically, so the untrusted compile cannot tamper with it), and the ephemeral scratch dir. The **writable project build lib is OFF the path**, so `import EmpiricistLean.Poison` cannot even resolve (compile-time FAIL). Gate (b2) resolves every DIRECT import via `lean --deps` and REQUIRES each resolved olean to sit under a pinned-trusted root (or be exactly the trusted `Basic`) → else `FAIL(import_trust)`; gate (d)'s driver additionally reports the module's TRANSITIVE import closure (`importRoots` + `empiricistImports`) and the harness rejects any import ROOT that is not pinned-trusted and any `EmpiricistLean.*` import other than `EmpiricistLean.Basic`. *Proven in isolation:* a poison planted on a trusted root (simulating a Lever-1 gap) so the import RESOLVES is still rejected `FAIL(import_trust)`.
  > - **LEVER 3 — residue sweep, fail-closed.** Each call uses a UNIQUE ephemeral dir (uuid4) removed in `finally`. Before trusting anything and after the run, the harness SWEEPS the shared module + build dirs for any UNEXPECTED file (anything not the committed `Basic.*`/pinned set) — a stray means a prior/concurrent call escaped its jail → `FAIL(residue)`, logged. *Proven:* a stray olean in the build lib fails the next verify closed.
  > Gate order (hardened): scratch → (b) SANDBOXED compile [errors/sorry] → (b2) import-trust [Lever 2] → (c) leanchecker kernel re-check → (d) axiom-whitelist + transitive import-closure over the checked olean → (e) PASS records statement. Golden suite adds three must-FAIL cases (poison-import harvest, unexpected import, compile-time-olean-write attempt) + integration tests (the full plant→harvest exploit now FAILs, sandboxed write denial, reachable-import rejection, residue sweep). **Residual (documented for a 5th pass):** the sandbox denies compile-time *writes* outside the workdir and *network*, but under the v0 `(allow default)` read posture it does NOT yet deny arbitrary on-disk *reads* or `mach-lookup` — so a compile-time secret-read/egress channel remains until the D8 CONTAINER-tier microVM lands (the host must hold no secrets the model shouldn't read; the env is already scrubbed of secrets).   > **UPDATE 2 (KERNEL-soundness fix, supersedes BOTH designs below — the trust anchor is now the Lean kernel).** The compiled-`collectAxioms` design (UPDATE 1) was itself defeated: **collectAxioms-only is UNSOUND against kernel-unchecked environment injection.** Untrusted compile-time metaprogramming (`run_cmd`/`elab`) can insert a constant with a FALSE type (`(1:Nat)=2`) but a clean, axiom-free value (`@Eq.refl Nat 1`) via `(← getEnv).addDeclCore (doCheck := false)`, `set_option debug.skipKernelTC true; addDecl`, or `withOptions (debug.skipKernelTC.set · true) (addDecl …)`. `Lean.collectAxioms` walks only the stored term → reports `axioms: []` → a proof of `False` certifies FORMALIZED (obfuscation-proof: a runtime-assembled option name defeats any string-scan). **Root cause:** auditing WHICH AXIOMS a term cites ≠ verifying the term was KERNEL-CHECKED against its stated type; `collectAxioms` over an attacker-mutated `Environment` is the wrong instrument. **The trust anchor is `lean4checker`** — merged into the toolchain since v4.28.0 and shipped as **`leanchecker`** (the standalone repo is deprecated; it has no v4.31.0 tag and its oleans are version-locked, so the version-matched instrument is the `leanchecker` in our pinned v4.31.0 toolchain — pinned durably in `lean/lean4checker.pin.json`, folded into `binary_hash`). `LeanVerifier.verify` is now a 4-gate pipeline over ONE compiled olean: (b) `lake env lean --json -o <olean> <scratch>` — `severity=="error"`→FAIL(diagnostics), `sorry` warning→FAIL(sorry); (c) `lake env leanchecker <Module>` re-checks the module's OWN added declarations through the real kernel starting from its trusted (pinned-mathlib) imports — nonzero/kernel-mismatch→FAIL(kernel_soundness) [THIS rejects the `1=2 := Eq.refl` injection: "declaration type mismatch, has type 1=1 but expected 1=2"]; (d) the compiled `axiom_audit` driver — now **importing the SAME kernel-checked olean** (not re-elaborating the source: a second frontend run could diverge from the checked olean under clock-branching metaprogramming) — reports the axiom SET (whitelist ⊆ `{propext, Classical.choice, Quot.sound}`;   > **UPDATE 1 (axiom-forgery fix, superseded by UPDATE 2 as the SOLE authority).** The in-band `#print axioms <decl>` approach is **UNSOUND**: it is an in-environment command the submitted source can **shadow**. Two adversarial reviews defeated it — (1) forging the `'<decl>' depends on axioms: [...]` info-diagnostic via `#eval IO.println` / `run_cmd Lean.logInfo`, and — fatally — (2) **redefining the `#print axioms` command itself** (`elab "#print " "axioms" ... => logInfo "...clean..."` or `macro_rules | `(#print axioms $n) => ...`), so the harness's own appended `#print axioms` dispatches to the attacker's elaborator and emits a fabricated clean line (nonce-anchored, exactly-one, whitelist-clean — full nonce-anchor hardening did NOT close it). Proven end-to-end: `theorem two : (1:Nat)=2 := evil.elim` (backed by `axiom evil : False`) certified as FORMALIZED. **Root cause:** any surface the harness re-elaborates in the tainted environment (`#print`, `#eval`, `run_cmd`, macros) is attacker-shadowable, so the axiom set MUST be computed by **compiled harness code** that walks the real kernel environment — never a re-elaboratable command. **Replacement (implemented):** a compiled `axiom_audit` `lean_exe` (`lean/EmpiricistLean/AxiomAudit.lean`) that elaborates the source with the real frontend (`Lean.Elab.runFrontend` under `IO.FS.withIsolatedStreams`) and computes the decl's axiom closure via compiled `Lean.collectAxioms` (exactly what `#print axioms` calls internally). It emits one nonce-framed JSON line (`AXIOM_AUDIT::<nonce>::{declFound,errors,axioms}`) to real stdout; the nonce is read from a file the driver deletes **before** elaborating the untrusted source, so compile-time IO cannot learn it and cannot forge an accepted line even via a direct `/dev/stdout` write + `IO.Process.exit`. `LeanVerifier.verify` runs `lake env <bin>/axiom_audit <scratch> <decl> <noncefile>` (same scrubbed env), parses the nonce-framed line as the SOLE axiom authority, and gates: errors → FAIL(diagnostics); `declFound` false → FAIL(decl_missing); axioms ⊄ whitelist → FAIL(axioms); no valid nonce line → FAIL(driver_result). `binary_hash` additionally covers `AxiomAudit.lean`. The must-FAIL golden suite adds the two command-override vectors + the driver-result output-injection vector (`verifiers/lean_goldens.py`). Verifier `version` bumped `1.0`→`2.0`.
